# 3. Данные в DVC и S3 кластера
Тут делал все аналогично семинару, только для своих данных. В репозитории на данный момент только dvc файл. Прикладываю скрин бакета в консоли S3. 
![Скрин бакета в S3](images\homework4\bucket_screen_s3.png)

Здесь была проблема, с которой достаточно долго боролся. Я хотел для убедительности увидеть, что .dvc файлов нет не только при docker run --rm, но и на кластере. Для этого необходимо было задеплоить образ с уже новой папкой datasets (в которой только dvc) на кластер. После смены папки, очевидно, надо пересобрать образ (так как именно в Dockerfile идет копирование данных в образ сервиса). Соответственно, я запускал последовательность команд ниже:
```
docker build -t bank-service:1.0 .
kind load docker-image bank-service:1.0 --name hw4
kubectl rollout restart deployment/bank-service
kubectl rollout status deployment/bank-service
```
Однако после их выполнения видел, что папка не менялась. Оказалось, что это происходит из-за того, что kind при load docker-image по умолчанию всегда поттягивает образ из ghcr (куда у нас обычно заливается образ в процессе ci). То есть он постоянно брал образ и последнего выполненного ci. Для исправления этого понадобилось добавить команду 
``` 
kubectl set image deployment/bank-service api=bank-service:1.0
``` 
Которая прямо привязывает именно этот образ к деплою.

# Восемь вопросов
1. Сначала получить определенную версию модели кодом по типу client.get_model_version с параметром version = = "N". Далее у модели будет аттрибут run-id - номер рана, на котором она тренировалась. В параметрах этого рана есть id коммита в git, в котором и можно найти хэш нужных данных в .dvc файле.
2. Данные не в образе, так как для многих задач они могут достаточно много весить и их нельзя кидать напрямую в среду выполнения. Если сделать git push раньше dvc push, то в репозитории будет хэш, который не ведет ни на какие реальные данные. Соответственно, упадет dvc pull.
3. Не очень понял разницы между бинарными проверками и проверками с порогом. У меня в целом бинарные и проверки датасета в pandera, и формат прохода модели ("прошло/не прошло"). Порог выбирал исходя из того, какие значения pr_auc видел при переборе гиперпараметров. То есть если лучший прогон отличался от 10 других не более чем на 0.003, значит все то, что меньше 0.003 - это вероятнее всего шум, поэтому гейн и нельзя брать слишком маленьким. Тут конечно нюанс, что есть дополнительная зависимость от того, а проще ли/сложнее ли стала модель. Если модель сложнее, ее сложнее поддерживать в проде, значит гейн должен быть большим. Но в нашем случае мы не можем перевести гейн в какие-то деньги, поэтому исходил из того, что считать/не считать шумом.
4. Pandera проверяет весь датасет для обучения и связана с процессом обучения. Pydantic проверяет параметры запроса и используется уже при инференсе. Они защищают разные этапы процесса, поэтому обе нужны.
5. Airflow занимается исключительно оркестраций, а для вычислений создает изолированную среду. Плюч из-за связи этой среды с кластером не приходится отдельно настраивать связь внутренних процессов Airflow (как было бы при запуске внутри него) с сервисами. Выкат новой модели не требует пересборки образа, так как ее параметры и конфигурация полностью хранятся в mlflow, а не в самом сервисе.
6. При использовании request_id в качестве метки в дашборде будет куча отдельных графиков для каждого запроса и он станет абсолютно неинтерпретируемым. В моем дашборде про инфраструктуру - рестарты контейнеров. Про сервис - количество запросов по тегам, RPS и задержка. Про модель - распределение скоров и доля положительных ответов.
7. PreStop нужен для того, чтобы сервисы не отправляли запросы в под за определенное время до его удаления. Обнволение маршрутизации в кластере и удаление пода не могут произойти в одно время. Поэтому если не сделать preStop, возникнет ситуация, в которых под уже удален, а в других сервисах при образщении сохраняется путь к нему. В процессе выката новый модели происходит плавный rollout подов. Старые готовятся к удалению, пока ждут готовности новых с новой моделью, и удаляются, как только новые достигли статуса ready.
8. Самым опасным местом сервиса я бы назвал загрузку модели из mlflow. Строго говоря, ее тренировочный датасет и данные, которые сервис ожидает при запросе, прямо не связаны. Поэтому всегда есть риск поменять формат тренировочных данных, оставив таким же формат входных. В случае, если добавились новые столбцы, то заметить проблему будет просто - модель будет просто падать с ошибкой. А вот если в каком то столбце поменялась величина измерения, или, например, тренировочный датасет собирался из одних источников, а запросы приходят из других со своими особенностями, то это можно будет заметить только по дата дрифтам и деградации модели.
