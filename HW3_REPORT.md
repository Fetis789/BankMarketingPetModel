### Три красных прогона с диагнозом

#### Некорретный Alias в ConfigMap
При смене alias на несуществующий в configmap в логах [запущенного workflow](https://github.com/Fetis789/BankMarketingPetModel/actions/runs/37517409190) видно, что новая нода сервиса падает с CrashLoopBackOff, однако на сервисе есть уже существующие ноды, которые продолжают работать. 
![Ошибка новой ноды](images\homework3\bad_alias_1.png)


При этом вначале при показе подробных логов выбирался только работающий под, поэтому более четко причину ошибки не увидел.
![Логи работающего пода](images\homework3\bad_alias.png)

Происходило это потому, что в диагностике была команда kubectl logs deploy/bank-service --tail=50 , которая выбирает только один под, которые все были от работающего контейнера. Я поменял в [следующем workflow](https://github.com/Fetis789/BankMarketingPetModel/actions/runs/37524082404/job/112476951334) это команду на kubectl logs deployment/bank-service -n default --all-pods=true -c api --prefix=true --tail=100 || true , которая показывает логи уже всех логов, и после нее уже увидел ошибку, которую приложил скрином и по которой все становится прозрачно.
![Итоговая ошибка с alias](images\homework3\alias_final_mistake.png)

### Вопросы
1. Tests и build не требуют доступа к моему локальному кластеру. Они могут создать необходимые контейнеры удаленно в github. Мы выбрали self-hosted runner, потому что он уже рядом с кластером и сам соединяется с GitHub по исходящему HTTPS — открывать Kubernetes API наружу не нужно. Он был создан для этого и у него есть шаблонные команды, позволяющие быстро его подключить.
2. --network kind нужен, чтобы подключить контейнер к кластеру, который запущен через kind. Сокет Docker нужен для того, чтобы Runner мог полноценно выполнять команды в том докере, в котором запущен кластер. --group-add 0 нужен для выдачи Runnerу привилегий, которые нужны для обращения к сокету Docker.
3. Это сделано для того, чтобы на втором деплое уже после загрузки секретов с первого деплоя не случилось падения. Без таких параметров в команде будет поломка в процессе деплоя в случае, если по заданным названиям в namespace, в котором запущен сервис (у меня это default), уже есть такие ключи.
4. Champion - текущая продовая модель. Challenger - модель, которая предоположительно лучше нее на тренировчных датасетах, которая проверятется в сервисе. Alias нужен для, того, чтобы не менять код сервиса постоянно при раскатке новых моделей. Иначе пришлось бы с появлением новых версий искать все участки кода, на которых делается импорт нужной версии модели в mlflow, и менять их на новую версию. А с alias достаточно только обозначить новыю версию как champion/challenger и все будет работать. Откат модели и rollout undo по сути перпендикулярны и не связаны. rollout undo отвечает за версию шаблона пода (откатывает ее назад) и меняет спецификацию развертывания пода (например, env переменные или requests). Можно откатить модель на том же шаблоне пода, а можно откатить шаблон пода без откатки модели.
5. В моем случае по настройкам будет использована модель-зашлушка из вложенного joblib файла. Но если бы его не было, то сервис падал бы сразу и даже не смог бы запуститься (так как load_model делается в lifespan перед yield), и в k9s показалось бы CrashLoopBackOff.
6. Сначала запрос из браузера идет 80 порт компьютера, откуда попадает на control-plane. Control plane через ingress кидает его на Service, заданный для MLFlow. Этот Service уже в свою очередь направляет его в сам Pod на targetPort. Настройка allowed-hosts нужна для фиксации имен, по которым можно образаться к ml_flow, core-allowed-hosts - с каких браузерных страниц разрешены запросы к серверу. 
7. На примере третьего прогона видим, что там было в определенный момент при 6 репликах CPU 90%/60%. В таком случае по формуле из лекции hpa должен был запустить еще 6*(90/60) - 6 = 3 ноды. Однако был параметр на maxReplicas = 6, поэтому он не мог это сделать. Уменьшаются реплики сильно дольше, чем увеличиваются, потому, что если уменьшать реплики быстро, то есть риск в силу скачащей нагрузки пропустить новые пики при повторном запуске сервиса (его остановка и повторный запуск будут занимать некоторое время, и если после одного пика будет другой, то сервис отсейлится с задержкой, хотя мог бы остаться на 6 репликах без необходимоси делать скейл заново)
8. В гит лежит код, различные технические файлы для контейнеров/кластеров, некоторые маленькие файлы с возможным проверочным контентом для сервиса. Из dvc в гите лежат различные технические файлы, но основное - это файл dataset.csv.dvc, в котором хранится указатель и хэш для восстановления реальных данных из хранилища. Для поиска данных для версии модели N нужно зайти на страницу mlflow этой версии и посмотреть там логи. В логах может быть как номер коммита в гит, по которому можно найти dvc файл, так и само название dvc файла. Затем нужно перейти в нужный коммит в гите и сделать в нем dvc pull - получим исходный датасет.
